# F15: Same-day editor → app pipeline (ready-to-post folder → draft items → one-tap approve)

Status: approved for build (Opus build run, 2026-11-14). The lead wrote it; Opus implementers build; slotting and approval hunks carry `// Fable to review`. **Migration 0009** (one column pair, see Data model). Line numbers are from `main` @ `b46ff25`; re-grep before citing.

## Where we start
- **The creator's loop:** record → his local editing chats ("workout video assembly", "trade recaps", Claude Code on his Windows laptop) render a clip he approves there → the clip should flow into the app with captions, a slot and warnings → he approves on the phone → the outbox posts it.
- **Laptop ingest exists:** `tools/ingest-agent` (`pnpm --filter @autopilot/ingest-agent ingest`) scans `INGEST_ROOTS`, runs `runQa` → `touchUp` (strips metadata into a clean copy) → `probeLocationTagKeys` must be empty → uploads `library/<sha256>.mp4` to R2 (`withRetry`) → `insert into media (..., status 'ready')`. Dedupe is a pre-check on `media.content_hash` (unique). It never touches source files.
- **Batches:** batch creation lives only in `scripts/skills/lib/batch-draft.ts:129` (always a new row; no unique `week_start`). `PgBatchStore.addItem` (`apps/web/lib/batches/pg-store.ts:175`) adds a draft with an empty caption and no time. `planTransition` (`transitions.ts:108`) gates approve on block warnings, handed-off rows and missing/past times. `tiktokDraft` lives in `batch_items.trial.tiktokDraft`.
- **Slots:** `assignSlots` (`packages/core/src/scheduler.ts:106`) places items on a fixed grid (`slotsPerDay` = 4 in `DEFAULT_CADENCE`) with per-platform stagger (YT +1 slot, TikTok +1 day) and caps of 4/day (Snapchat 1). There is no "not before / not after" constraint, and `normalizeCadence` has no upper bound on caps.
- **Push:** `ALERT_KINDS` + `PUSH_KINDS_DEFAULT` in `packages/core/src/types.ts:78,97`; `alerts.kind` has no CHECK, so a new kind needs no migration.

## Goals
1. A clip the creator approved in an editing chat shows up as **draft** items in the app within ~10 min, captioned, slotted inside his `when`/`earliest`, with the usual warnings.
2. **One tap** in the app approves and schedules it, through `planTransition`. Nothing else approves.
3. Same-day posts fit next to the weekly batch: up to 3 scheduled + 2 same-day per platform per day, behind a labelled cap setting.
4. Idempotent end to end: the same render (content hash) never produces a second item for the same platform, however often the agent runs.

## Non-goals
- Approving in the agent, or treating `approvedInEditor` as app approval.
- Deleting anything: the source file is moved to `_ingested/` only after a confirmed upload; nothing in R2 or the DB is deleted.
- Writing captions on the server (AI split, `docs/decisions.md` §4): a missing caption is flagged, not generated.
- Watching the folder continuously (Task Scheduler runs the one-shot every 10 min).
- Snapchat publishing (stays assisted; the item lands in the handoff list once approved).

## The contract (version 1; keep identical, a content session writes against it)
Each approved render is `<name>.mp4` plus `<name>.post.json` in the `ready-to-post` folder (laptop env `INGEST_READY_DIR`):
```json
{ "version": 1,
  "pillar": "trade-recap | workout-log | physique | single-set | yap | other",
  "platforms": ["instagram","youtube","tiktok","snapchat"],
  "when": "today | tomorrow | this-week",
  "earliest": "HH:MM (optional, creator-local)",
  "caption": { "instagram": "…", "tiktok": "…", "youtube": { "title": "…", "description": "…" }, "snapchat": "…" },
  "soundInApp": false,
  "approvedInEditor": "<ISO timestamp>",
  "source": "workout-assembly | trade-recaps | manual" }
```
Validation (zod, `tools/ingest-agent/src/ready/sidecar.ts`): `version` literal 1; `pillar`, `when`, `source` enums; `platforms` non-empty, unique, subset of the four; `earliest` `^([01]\d|2[0-3]):[0-5]\d$` if present; every `caption` key optional and each string may be empty; `approvedInEditor` ISO datetime; unknown keys rejected (`.strict()`), so a typo fails loudly instead of being ignored. An invalid sidecar leaves both files in place and prints one `FAIL <name>: <zod path>: <message>` line.

## Interfaces
```ts
// packages/core/src/scheduler.ts (additions; existing behaviour unchanged when absent)
export interface ScheduleItem {
  // ...existing
  window?: { notBefore: string; notAfter: string }; // ISO instants; placement only inside [notBefore, notAfter)
  sameDay?: boolean; // editor item: ignore stagger; may use the flex grid (below) when grid slots are full
}
// Flex grid for sameDay items: candidate times every `minGapMinutes` inside each posting window,
// first one >= window.notBefore that is >= minGapMinutes from every existing/assigned post on that
// platform and keeps the day under dailyCaps[platform]. Grid slots are tried first.

// packages/core/src/cadence.ts
export const CAP_LIMITS: Record<Platform, number>; // instagram 25, youtube 10, tiktok 15, snapchat 1 (research.md limits, with margin)
// DEFAULT_CADENCE.dailyCaps → instagram 5, youtube 5, tiktok 5, snapchat 1. normalizeCadence rejects a cap above CAP_LIMITS.
// A stored `cadence` settings row overlays the default, so the VPS keeps its stored caps until the creator changes the setting.

// packages/core/src/types.ts
// ALERT_KINDS += "ready-for-approval"; PUSH_KINDS_DEFAULT += "ready-for-approval"

// tools/ingest-agent/src/ready/plan.ts (pure)
export interface ReadyInput { sidecar: Sidecar; contentHash: string; mediaId: string; now: Date; timeZone: string;
  cadence: CadenceSettings; existing: ExistingPost[]; lint: (text: string, kind: "caption" | "title", platform: Platform) => LintResult }
export interface PlannedItem { platform: Platform; ingestKey: string; caption: string; title: string | null;
  scheduledFor: string | null; weekStart: string; tiktokDraft: boolean; flags: EditorFlag[] }
export type EditorFlag = "needs-caption" | "add-sound-in-app" | "no-slot" | "lint-error" | "tiktok-draft-limit";
export function planReadyItems(i: ReadyInput): PlannedItem[];
export function ingestKey(contentHash: string, platform: Platform): string; // `${contentHash}:${platform}`
```
**`when` → window (creator-local, DST-safe via `localToUtc`):** `today` = [max(now, today `earliest`), end of today); `tomorrow` = [tomorrow `earliest` or start, end of tomorrow); `this-week` = [max(now, today `earliest`), end of the local Sunday). `weekStart` = local Monday of the assigned slot's day (of the window start when unslotted). No slot inside the window → `scheduledFor: null` + flag `no-slot` (never silently rolled into a later day; the app offers "Move to tomorrow").

**Per platform:** caption = `caption.instagram|tiktok|snapchat`, YouTube caption = `youtube.description` and title = `youtube.title`. Empty or missing → flag `needs-caption`. `soundInApp: true` → TikTok `tiktokDraft: true` (Creator Inbox draft), IG/YT flag `add-sound-in-app`. TikTok drafts: if ≥ 5 TikTok draft items are already scheduled in the 24 h before the slot → flag `tiktok-draft-limit` (Zernio allows 5 pending per 24 h).

## Data model (migration 0009_editor_ingest.sql)
```sql
alter table batch_items add column ingest_key text;   -- `${content_hash}:${platform}`, editor items only
alter table batch_items add column origin text;       -- 'editor' | null (weekly batch)
create unique index batch_items_ingest_key_uq on batch_items (ingest_key) where ingest_key is not null;
```
Editor metadata goes in `batch_items.trial.editor = { source, pillar, when, earliest, approvedInEditor, flags }` (jsonb already exists). The unique index is the idempotency guarantee: the writer uses `insert ... on conflict (ingest_key) where ingest_key is not null do nothing`, so a re-run, a second laptop or a race can't double an item. A rejected item keeps its key: re-dropping the same render does nothing (re-render to post it again).

**Rolling batch for a week:** inside one transaction, `pg_advisory_xact_lock(hashtext('batch-week:' || week_start))`, then the newest `batches` row with that `week_start` and status not `archived`, else insert a `draft` batch. Items are added as `draft`; the batch row's status is recomputed the way `PgBatchStore.apply` does (re-use, don't copy).

**Media row:** `insert ... on conflict (content_hash) do update set r2_key = excluded.r2_key where media.r2_key is null returning id` (a row from the old ingest keeps its values).

## Laptop side: `pnpm ingest:ready` (one-shot)
For each `<name>.mp4` with a `<name>.post.json` in `INGEST_READY_DIR` (top level only; `_ingested/` and dot-files skipped; an mp4 without a sidecar is reported `WAIT` and left alone):
1. Validate the sidecar. Hash the mp4.
2. If every planned `ingest_key` already exists → `SKIP <name> (already ingested)` and move the files to `_ingested/` (the upload was proven by the earlier run).
3. `runQa` → `touchUp` → `probeLocationTagKeys` must be empty → upload `library/<hash>.mp4` with `withRetry` → verify with a `HEAD` (size > 0) → upsert media.
4. `planReadyItems` with `existing` = non-rejected items with a time in the window's weeks → write items + `trial.editor` + one `ready-for-approval` alert per new item (`unique(kind, batch_item_id)` makes it idempotent). Lint errors don't block ingest: they become block warnings in the app as usual.
5. Only after steps 3-4 succeeded: move `<name>.mp4` and `<name>.post.json` into `ready-to-post/_ingested/` (`fs.rename`; on a name clash append `-<hash8>`). Any failure → both files stay where they are and the line says `FAIL <name>: <stage>`.
Output: one line per file, then `ingest:ready: N new · N skipped · N wait · N fail`; exit 1 on any FAIL. Env: `INGEST_READY_DIR`, `TZ_CREATOR`, `DATABASE_URL`, `R2_*` (names only; same as the old ingest). `--dry-run` plans and prints without upload, DB writes or moves.

## App side
- **"From your editors" card** on Home (above "Next up") and on `/batches/[id]` (top), listing `origin = 'editor'` items in `draft`: preview (poster/video via the existing session-guarded media route pattern, or the library thumbnail if one exists), platform, caption (first 2 lines), slot ("Today 18:30" in the creator zone), source chip, warnings (block in red, warn as chips: `caption.missing` "Needs caption", `sound.in-app` "Add sound in app or post as-is", `slot.none` "No free slot today", lint).
- **Actions** (server actions, `requireSession()` first, through `planTransition` + `PgBatchStore.apply`):
  - **Approve & schedule**: `approve` for the item's ids (one render = up to 4 items; one tap approves the render's items that have no block warning and says which stayed). Block warnings are never skipped.
  - **Edit caption**: the existing `edit` transition.
  - **Move to tomorrow**: re-slot with `assignSlots` (window = tomorrow, `sameDay: true`, existing posts) → `edit {scheduledFor}`; no slot → error message, nothing changed.
  - **Reject**: the existing `reject` (no delete).
- **New warning codes** in `computeWarnings`: `caption.missing` (block; empty caption on any platform except Snapchat; empty title on YouTube), `sound.in-app` (warn; `trial.editor.flags` has `add-sound-in-app`), `slot.none` is the existing `time.missing` with editor wording.
- **Cap setting**: a labelled control "Daily posts per platform (cap)" on a small `/more/settings` page: per-platform number inputs bounded by `CAP_LIMITS`, showing the stored value (or the default if no row), saving into the `cadence` settings row (merge, row-locked, like `updateEngagement`). **Audit:** a new page-only alert kind `settings-change`, inserted already acknowledged, message e.g. "cap instagram 4→5" (same pattern as the `engagement-mode` audit row). Never pushed. The new caps apply to the next slotting; already-scheduled items aren't moved.
- **DM drafts toggle** on `/inbox/dms`: "Turn on DM drafts (read-only, never sends)" switch → sets `engagement.dmPollVerified` via `updateEngagement`, writes a `settings-change` audit alert "dm drafts on|off". Default off.
- **Push**: `ready-for-approval` is in `PUSH_KINDS_DEFAULT`; the alert message is "New from <source>: <pillar> · <platforms>" (no caption text, no place).

## Acceptance (whole item)
1. Dropping a valid render + sidecar in `ready-to-post` and running `pnpm ingest:ready` twice yields one draft item per platform, slotted inside `when`/`earliest`, files in `_ingested/`.
2. Nothing publishes until **Approve & schedule** is tapped; block warnings still block.
3. A failed upload leaves the source files in place; nothing is deleted anywhere.
4. Typecheck, tests (with `DATABASE_URL`), both simulations, web build, leak scanner green.

## Open questions (decided by the lead)
1. Batch per week or a dedicated "editor" batch? **Per week (rolling), so the week view and caps see everything.**
2. When `today` has no slot left? **Leave unslotted with `no-slot`; the creator taps "Move to tomorrow". Never roll silently.**
3. Re-dropping a rejected render? **No-op (key exists). Re-render to post again.** Documented in the runbook.
4. Cap default? **5/day IG/YT/TikTok in code, Snapchat 1. The VPS keeps its stored `cadence` caps (4) until the creator raises them in Settings** (Needs you), so live behaviour doesn't change silently.
