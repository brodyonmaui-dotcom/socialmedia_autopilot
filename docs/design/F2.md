## Where we start
- Drafts arrive from the **weekly-batch skill**: `logs/batch-<week>.json` → `check` → `review` → `pnpm schedule-batch --write` → `pnpm skill:weekly-batch create`. `createDraftBatch` (scripts/skills/lib/batch-draft.ts:118) inserts `batches(status 'draft')` + one `batch_items(status 'draft')` per platform post, all with times.
- **No approval path in the app.** The only write path is `scripts/schedule-catchup.mjs --approve` (:44-46), a raw UPDATE.
- The outbox fires any `batch_items.status = 'approved'` row and **ignores `batches.status`** (apps/worker/src/jobs/outbox.ts:94-101).
- Web pages exist for library, touch-up, research and analytics. There are no batch, alert or inbox pages, and the app has no auth (actions.ts:18 `TODO(F2)`).
- Caddy basic auth on `/app*` is the whole gate today (`docs/runbooks/dashboard-password.md`).
- `tiktokDraft` is rejected by `checkDraft` (batch-draft.ts:73-76). The worker, however, already reads `trial.tiktokDraft` (outbox.ts:42,89) and the adapter supports drafts.

## Goals
1. **Approval UI, phone first.** `/app/batches` lists batches. `/app/batches/[id]` shows a week grid (day → slots) of post cards with:
   - inline edit of caption, title and time;
   - approve one, approve all;
   - reject, and pull back (unapprove);
   - warnings: format/QA, location, missing sound, duplicate, cap breach, `{{…}}` placeholder, past time, missing clean file.
2. **Batch builder, light.** Captions are still written by the skill, not the web. The web only:
   - adds a library clip to a draft batch for chosen platforms (empty caption + a lint error until filled);
   - removes a post (→ `rejected`, never deleted);
   - "Fill missing times" runs `assignSlots` server-side, the same logic as `schedule-batch`.
3. **Approval means something.**
   - Approving stamps `approved_at`, the session and an audit event.
   - The worker fires an item only if the item is approved **and** its batch is approved.
   - Editing an approved item drops it back to `draft`.
4. **Single-user login: passkey (WebAuthn) app session behind the Caddy gate.**
   - Every page and every server action checks the session.
   - Enrolment needs a one-time code from a CLI run on the VPS.
5. Reconcile `tiktokDraft` so sound-dependent TikToks can be approved as Creator Inbox drafts.

## Non-goals
- AI caption generation in the web. That stays the `weekly-batch` skill.
- Multi-user accounts, roles, OAuth or social login. Removing the Caddy gate (see OQ1).
- Drag-and-drop grid; Snapchat handoff UI (M2); PWA push (still open from F4).
- Editing posts already handed to a platform: YT/TikTok hand off up to 24 h early (engine.ts:92). The UI shows "scheduled on platform; change it in Studio/TikTok".
- Deleting rows (non-negotiable 6). Reject is a status.

## Auth decision (recommended: keep the gate, add an app session)
| Option | Verdict |
|---|---|
| **A. Keep Caddy basic auth + add passkey app session (rec.)** | Two independent layers: the password lives in Caddy, the device-bound passkey in the app. The app session also gives CSRF-safe server actions and an audit identity. If one layer has a bug, the other still holds. The cost is one more prompt per new device. |
| B. Passkey replaces the gate | Fewer prompts, but the app's own code becomes the only guard of `/app`. Revisit after F7 has reviewed the auth code (OQ1). |
| C. Password + TOTP in the app | More code and secrets to store. With the gate in place, the passkey already makes a second factor. |

**Flow**
- **Enrol**
  - On the VPS: `docker compose exec web pnpm auth:enroll` writes a hashed single-use code (15 min) and prints it to *that terminal only*.
  - On the phone: `/app/login` → "Add this device" → enter the code → WebAuthn register.
  - Allow at most 5 passkeys.
- **Login**
  - `/app/login` → WebAuthn assertion → `auth_sessions` row.
  - The cookie is `ap_session`: random 32 bytes, base64url, `HttpOnly; Secure; SameSite=Strict; Path=/app`. Only the sha256 is stored.
  - Sliding 30-day expiry with a 90-day hard cap.
- **Check**
  - `middleware.ts` checks only that the cookie exists and is well-formed, otherwise it redirects to `/app/login`. Next 15.1 middleware is edge-only, so it can't reach pg.
  - `requireSession()` validates against the DB in every page and server action (node runtime).
- **Recover:** `pnpm auth:revoke-all` revokes all sessions and passkeys, then `auth:enroll` again.
- **Rate limit:** at most 10 failed assertions or enrol attempts per 15 min in total. Then refuse, and raise an alert of new kind `auth`.
- **RP id / origin** come from `DOMAIN` (env, never committed). For local dev: `localhost`.
- New deps: `@simplewebauthn/server` and `@simplewebauthn/browser`, at exact versions at least 2 weeks old. No paid services.

**Rules in `planTransition`**
- `approve`: the item must be `draft` with zero `block` warnings. A placeholder, a past or missing time, a lint error, cap breaches, or a missing clean file (no `r2_key` → broken `mediaUrl`, outbox.ts:77) all block.
- `approve-all`: approves every draft item with no blocks. It returns the list of skipped items with reasons. The batch becomes `approved` when ≥1 item is approved.
- `edit`: allowed when the item is `draft` or `approved` and not handed off. An approved item goes back to `draft`.
- `unapprove`: `approved` or `queued` (not yet claimed) → `draft`. It refuses `publishing`, `published`, `unknown`, `failed` and handed-off items.
- `reject`: `draft` or `approved` → `rejected`.
- `apply` runs `update … where id=$1 and status=$from`. If any update returns 0 rows, the whole transaction is aborted and "changed underneath you, reload" is shown. That covers the race with the worker's `claim`.

create table auth_credentials (id uuid primary key default gen_random_uuid(), credential_id text not null unique,

## Acceptance criteria (whole item)
1. On a phone, behind the Caddy prompt: enrol a passkey with a CLI code → log in → `/app/batches` → open the DRAFT batch from the skill → fix a flagged caption inline → Approve all → the confirm sheet shows counts → the batch is `approved`.
2. Without a valid session, every `/app` page redirects to `/app/login`, and every server action refuses. This is proven by the static test plus unit tests.
3. The worker fires only items with item `approved` + `approved_at` + batch `approved`. `simulate-week` still shows 0 double-posts and 0 cap breaches.
4. No approval path skips the block warnings: placeholder, location, past time, missing clean file, cap breach.
5. No secrets or enrol codes in logs; session tokens are stored hashed only; nothing is deleted (reject = status).
6. `pnpm typecheck`, `pnpm test`, `pnpm simulate-week` are green. `docs/runbooks/login.md` exists. Migration 0006 is listed as pending for the VPS (the creator runs it).
