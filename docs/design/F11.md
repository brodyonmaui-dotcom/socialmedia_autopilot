Status: draft (Opus prep run, 2026-11-13). **Safety-critical: Fable finalizes and builds it.** Line numbers are for `main` @ `b455456`; re-grep before citing. Probably **no migration** (see Data model).

## Where we start
- **Runbook.** `docs/runbooks/failed-or-unknown-post.md:5` says "Re-approve" has no app button yet, so ask in chat before hand-editing a row. Steps `:10-17`: read `last_error`, check the platform by hand (IG profile; YT Studio, including private/scheduled; TikTok profile); if it exists, record it as published; if it's missing, re-approve. Two stale facts: `:7` says "3 attempts" (the code does 4, `packages/core/src/outbox/policy.ts:21-28`), and `:17` points to a YouTube note in `apps/worker/src/jobs/outbox.ts` that doesn't exist (the note is at `packages/adapters/src/youtube.ts:37`).
- **Transitions refuse every handed-off row.** `handedOff` = `platform_post_id != null` or status in `publishing|published|unknown|failed` (`apps/web/lib/batches/types.ts:68-72`). `approve` refuses at `transitions.ts:56`, `reject` at `:101`, `unapprove` at `:111`, `edit` at `:122`. No transition goes `failed → draft`.
- **The store.** `PgBatchStore.apply` (`apps/web/lib/batches/pg-store.ts:82-116`) runs one transaction with a conditional `update … where id and batch_id and status = from` (`:99`); `rowCount != 1` → `ConflictError`. It writes `status`, `updated_at`, `approved_at`, `approved_session` and patched caption/title/time, and never touches `attempts`, `last_error`, `platform_post_*` or `idempotency_key`. Events go to `batch_item_events` (`:101-104`).
- **Idempotency key.** It's a DB default (`0001_init.sql:40`, `gen_random_uuid()`, unique `:48`). No code regenerates it. TikTok sends it as `Idempotency-Key` (`packages/adapters/src/tiktok.ts:74`); Zernio's window is 24 h (F7 A5, `docs/design/F7.md:32`).
- **What the engine would do with a reset row today** (`packages/core/src/outbox/engine.ts`):
  - The existence check runs before a send only when `attempts > 0` and the adapter has `findExisting` (`:203-221`).
  - `attempts` is never reset, so a `failed` row (attempts 4) that's re-approved gets **one** try: a rejection gives attempts 5 ≥ 4 → `failed` at once (`policy.ts:91`). A timeout → `unknown` again.
  - `approved_at` is cleared on `→ draft` (`pg-store.ts:92`) and re-stamped on approval, so the worker gate (`listDue`) works unchanged.
- **Existence checks per platform.** Only IG has one: `findExisting` lists the last 25 media and matches the normalised caption within ±36 h of `scheduled_for` (`packages/adapters/src/instagram.ts:133-142`). YouTube has none (`youtube.ts:37`, test `youtube.test.ts:93`). TikTok/Zernio has none (it relies on the key). Snapchat never reaches the outbox.
- **UI.** `PostCard.tsx:42-48` shows handed-off rows with no buttons and the text "scheduled on the platform; change it in Studio/TikTok", which is wrong for `failed`. `loadBatch` doesn't select `attempts` or `last_error` (`pg-store.ts:46-47`). The confirm-sheet pattern is `apps/web/app/batches/ui/ApproveBar.tsx:48-88`.
- **Alerts.** `final-failure` (`engine.ts:277`, `:226-227`) and `unknown-outcome` (`:159`, `:283`), deduped per kind + item (`0005_outbox.sql`, `unique(kind, batch_item_id)`).

## Goals
1. **Reset to draft ("I checked, it's not there").** A new action on a `failed` or `unknown` item, only when `platform_post_id is null`:
   - `status → draft`, keeping **the same row and the same `idempotency_key`** (F7 A5: never insert a new row and never regenerate the key).
   - `approved_at`, `approved_session` → null (as today's `→ draft`). `next_attempt_at` → null.
   - `attempts` → **1** (see OQ1): it keeps the engine's existence check before the next send (`attempts > 0`) and leaves 3 real tries. The old count goes in the event detail.
   - `last_error` → null on the row; its sanitised text goes in the event detail (it's already sanitised at write time, F7 B1).
   - One `batch_item_events` row, `kind='reset-checked'`, `from_status` = failed|unknown, `to_status='draft'`, `session_id`, and `detail {attemptsBefore, lastError, checked: string[], autoCheck}` (see goal 3).
   - The matching `final-failure` / `unknown-outcome` alert is acknowledged (`acknowledged_at = now()`) in the same transaction, so the alerts count drops. If F8 is in, use its acknowledge helper; otherwise a plain conditional update.
   - Then the item is an ordinary draft: the creator fixes the time/caption if needed and approves it through the normal F2 flow. **The reset never approves.**
2. **Record as published ("I checked, it IS there").** The other runbook branch:
   - `failed|unknown → published` with `platform_post_url` (required) and `platform_post_id` (optional), with the URL validated per platform: `https:`, host `instagram.com` / `www.instagram.com`, `youtube.com` / `www.youtube.com` / `youtu.be` / `studio.youtube.com`, `tiktok.com` / `www.tiktok.com`. Anything else is refused (not dropped: here the URL is the evidence).
   - Event `kind='record-published'`, alert acknowledged as in goal 1.
3. **A confirm sheet that lists what was checked.** It opens from the item card and shows:
   - platform, status, attempts, the sanitised `last_error`, the scheduled time, the last 6 characters of the key (so a later TikTok/Zernio lookup can be matched);
   - a per-platform checklist that must be ticked, all boxes, before "Confirm reset" enables (these strings go into `detail.checked`):
     - **Instagram:** "Profile grid and Reels tab (newest first)"; "Trial reels (Professional dashboard → Trial reels)"; "Caption search isn't needed: the app checked the last 25 posts (result below)".
     - **YouTube:** "YouTube Studio → Content, **including Private and Scheduled**"; "Upload drafts / processing in Studio". (A failed upload can still have created a private video.)
     - **TikTok:** "TikTok profile, including Drafts/Inbox if it went as a draft"; "Zernio dashboard → Posts, matching the key ending …"; "More than 24 h since the last try, or the post is confirmed absent in Zernio" (the key's window, F7 A5).
   - **IG automatic check:** the server action runs the IG adapter's `findExisting` (read-only GET) before showing the sheet and again inside the reset action. A hit refuses the reset and offers goal 2 with the found URL prefilled. A lookup error shows "automatic check failed; check by hand" and keeps the reset allowed only after the manual boxes are ticked; the result is stored in `detail.autoCheck` (`'not-found' | 'error' | 'n/a'`). It never posts.
4. **Card fixes.** For `failed` / `unknown`, `PostCard` shows the status, attempts and sanitised `last_error` (add both to `loadBatch`), plus the two buttons "Not on the platform → back to draft" and "It's there → record it". It no longer says "scheduled on the platform" for these.
5. **Runbook.** Update `failed-or-unknown-post.md`: the buttons replace the hand-edit; fix "3 attempts" → 4 and the YouTube pointer.

## Non-goals
- Any automatic retry of `unknown`. `unknown` stays manual forever (non-negotiable 3).
- Deleting rows or posts (non-negotiable 6). Nothing here deletes.
- A YouTube or TikTok existence API. YouTube has no documented lookup by our key, and Zernio's post-list lookup isn't verified (OQ3). Those stay manual checks.
- Resetting `publishing` (the engine's stale path owns it) or `published` rows.
- Bulk reset. One item at a time, on purpose.

**Rules**
- Never generate or change `idempotency_key`. A test reads the SQL in `pg-store.ts` and asserts the column isn't in any `set` list.
- The reset is conditional on `status in ('failed','unknown') and platform_post_id is null`. 0 rows → refuse with "changed underneath, reload".
- The IG lookup runs **inside** the reset action as well as before the sheet (the sheet could be stale). A hit refuses.
- `DRY_RUN` doesn't matter here: no platform writes happen. The IG lookup is a GET; with no IG credentials it reports `'error'`.
- Text shown in the sheet comes from the DB (already sanitised); never show raw upstream bodies.

## Data model
No new table or column. New `batch_item_events.kind` values `reset-checked` and `record-published`: add them to `BatchItemEventKind` (`packages/db/src/types.ts:65`). The status CHECK already allows `draft` and `published`. If Fable prefers a separate `retry_budget` column over the `attempts = 1` trick (OQ1), that's migration **0009** (F8 owns 0008).

## Acceptance criteria (whole item)
1. A `failed` IG item: open → sheet → app check "not found" → tick boxes → confirm → it's a draft with the same key → approve → the next (fake) tick checks IG first, then publishes once.
2. An `unknown` YouTube item: the sheet requires the Studio "Private and Scheduled" box; the event lists the ticked boxes.
3. "It's there" with a valid URL → `published`, audited; a URL on another host is refused.
4. The key never changes (test), nothing is deleted, and `unknown` is never retried without the creator's tap.
5. `pnpm typecheck`, `pnpm test`, `pnpm simulate-week` are green.

## Open questions (recommended default in **bold**)
1. **How to give a reset item a fresh retry budget and still force the existence check?** **`attempts = 1` on reset**, with the old count in the event: the engine's `attempts > 0` guard then runs `findExisting` (IG) before the first resend, and 3 tries remain. The alternative is a `retry_budget`/`reset_at` column (migration 0009) and an engine change: cleaner but touches the engine. Pick the column only if the engine is being changed anyway.
2. **Run the IG automatic check from the web container?** **Yes, read-only, inside the action.** The web container already gets the same `.env` (`env_file`); it's one GET of the last 25 media. Without credentials, the check reports "error" and the manual boxes decide.
3. **Zernio post lookup.** **Leave it manual for now.** If `docs.zernio.com` documents a `GET /posts?…` that can match our key, verify it (non-negotiable 7) and add it as TikTok's automatic check in a later item.
4. **Should a reset `unknown` TikTok item within 24 h of the last try be blocked?** **No block, but a required checklist box** ("> 24 h since the last try, or confirmed absent in Zernio"). Inside the window, Zernio deduplicates on the same key, which is the safe direction.
5. **Acknowledge the alert on reset?** **Yes, in the same transaction**, so the home count reflects reality. The event row is the audit trail.
