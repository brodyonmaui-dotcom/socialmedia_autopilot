## Goals
1. **`/alerts` page (phone first).**
   - Two tabs, Open (default) and Acknowledged (last 30 days).
   - Kind chips filter the list, and each chip shows its count.
   - Each card shows kind, source (platform/service), age, message and a link to `/batches/[batchId]` when `batch_item_id` is set.
   - Actions: "Acknowledge" on a card, and "Acknowledge all shown" behind a confirm sheet with the count.
   - Acknowledging stamps `acknowledged_at` and `acknowledged_session` (the audit).
2. **Home badge.** The existing count becomes a link to `/alerts` with a red badge when > 0.
3. **Web Push.**
   - VAPID keys come from env **names only**: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`.
   - Subscriptions are stored in `push_subscriptions`.
   - A worker job, `alert-push`, sends each new pushable alert **once**, using the `alerts.pushed_at` dedupe column. Alerts that arrive together are bundled into one notification.
4. **Phone side.**
   - Service worker `apps/web/public/sw.js`, served at `/app/sw.js` with scope `/app/`. It handles `push` → `showNotification` and `notificationclick` → open `/app/alerts`.
   - An "Enable notifications" button. It's a client component and must be triggered by a tap, because iOS requires a user gesture. It shows a hint when the app isn't installed to the Home Screen.
   - A "Send test notification" button.
5. **PWA icons.** 192 and 512 PNG plus a maskable icon and an `apple-touch-icon`, generated from a plain monogram (no photo, no place). This makes the app installable, which iOS Web Push requires.
6. **Payload privacy.**
   - Push travels through Apple/Google push services, so the payload holds only `{count, kinds[], sources[], url:"/app/alerts"}`. It never holds `message` text, captions, comment text, ids or URLs other than `/app/alerts`.
   - Subscription endpoints and keys are never logged; the job logs counts only.

## Non-goals
- Multi-user, email, SMS, or third-party notification services (no paid service).
- Quiet hours and per-kind schedules in v1 (OQ2).
- A retry/reset action for `failed`/`unknown` items. It's a separate design (see `docs/prep/run-3-plan.md`); the alerts page only links to the batch.
- Changing which code paths raise alerts, or changing alert dedupe semantics in the writers.
- Deleting alert rows. Acknowledge is a timestamp.

**Rules for `runAlertPushOnce`**
- **Disabled path.** If push is disabled (VAPID unset), claim nothing, log once `[alert-push] disabled: VAPID_* not set`, and return.
- **Claim before send (at-most-once).** A crash between claim and send loses one notification, and the alert is still on the page. That's safer than double pages. Never re-push a row that has `pushed_at`.
- **Bundling.** All claimed alerts go into **one** notification per subscription, with a 1 h TTL and urgency `high` for `engagement-kill`/`unknown-outcome` (`normal` otherwise).
- **Push-service responses:**
  - 404/410 → revoke that subscription.
  - other non-2xx or thrown → count as failed; log `[alert-push] failed n=…` with no endpoint.
  - 2xx → `markSuccess`.
- **Age cutoff.** `created_at` older than `maxAgeH` is never pushed. This, plus the 0008 backfill, prevents a burst on first deploy.
- **Token-health re-inserts.** A daily re-inserted token-health row is a new row, so it pushes once a day while the problem persists. That's intended: it acts as a daily reminder until it's fixed.
- **Dry-run.** Push runs in dry-run too (OQ3), because it's a private notification to the creator, not a public action.

## Data model: `packages/db/migrations/0008_alerts_push.sql`
```sql
alter table alerts add column pushed_at timestamptz,
                   add column acknowledged_session uuid references auth_sessions(id) on delete set null;
-- don't page for history on first deploy
```

## Open questions (recommended default in **bold**)
1. **Which kinds push by default?** **`engagement-kill`, `unknown-outcome`, `final-failure`, `token-health`, `auth`.** `cap-breach`, `duplicate`, `engagement-failure`, `engagement-unknown` and `engagement-mode` stay page-only, and are configurable via the `alert_push` setting. `engagement-unknown` is the closest call: add it if shadow mode ever goes live.
2. **Quiet hours?** **None in v1.** The pushable kinds are all "act soon", and iOS Focus already handles nights. Revisit if a daily token-health reminder lands at a bad hour. Any time-of-day logic would need `TZ_CREATOR` from env, never in code or docs.
3. **Push in dry-run?** **Yes.** It's private to the creator and read-only toward the platforms.
4. **Library?** **`web-push` (MIT, free, the standard VAPID/aes128gcm implementation), worker-only, at an exact version published at least 2 weeks ago.** Ask the creator if the lead isn't sure new runtime deps are pre-approved (F2 had an explicit approval). The fallback is a ~150-line VAPID JWT + aes128gcm encrypt on `node:crypto`, which is more code to review.
5. **Does basic auth interfere with service-worker registration on iOS?** **Expect no**, because the SW script fetch is same-origin and the Caddy credentials are already cached. Verify on the phone in the demo. If registration fails, the fallback is a Caddy `handle /app/sw.js` that serves the file without basic auth (it's static and holds no data). That's a Caddyfile change, so ask first, and remember `docker compose restart caddy`.
6. **iOS facts** (Web Push only for Home-Screen PWAs, iOS 16.4+, permission only from a tap): **verify against Apple/WebKit docs at build time** (non-negotiable 7) and add a line to the `docs/research.md` verification log.
