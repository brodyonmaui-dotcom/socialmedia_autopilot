# F18: Posting you can trust (missed-slot guard, worker heartbeat, posting-status banner)

Status: spec, 2026-11-19. Trigger: approved TikTok/YouTube posts for the morning of 2026-11-19 never went out, and nothing in the app said so. Most likely cause: the worker is still in dry-run (the first-real-post runbook ends by switching back to dry-run), which only logs "would publish". Second risk: switching live with a backlog would fire every overdue approved post at once (no lateness bound in `isDueNow`, `packages/core/src/outbox/engine.ts:94`; `listDue` has no lower bound).

## Goals
1. **Missed-slot guard (engine).** A post with `status 'approved'` whose `scheduledFor` is more than `missedGraceMs` (default 60 min) in the past is **not sent**. It stays `approved` (no status change, no migration), is counted in `TickResult.missed`, and raises one `missed-slot` alert per item (dedupe per item; check how `store.recordAlert`/the pg alert sink dedupes `cap-breach` and use `(kind, batch_item_id)` uniqueness the same way). Check it **before** the cap guard, in dry-run and live alike. `queued` retries are not affected (their lateness is the backoff). The alert message: `post missed its time (<platform>, <scheduled local HH:MM date>); move it in the calendar` — no caption, no id beyond what alerts already carry.
2. **Late but within grace (native platforms: YouTube, TikTok).** When sending, if `scheduledFor < now + 5 min`, hand the adapter a copy with `scheduledFor = now + 5 min` (YouTube needs a future `publishAt`; Zernio the same). The DB row keeps its original time. Instagram is unchanged (fires at once).
3. **Worker heartbeat.** The worker upserts `settings` key `worker_status` at startup and at the end of every outbox tick: `{ "mode": "live" | "dry-run", "reason": string | null, "startedAt": ISO, "lastTickAt": ISO, "missed": number, "dueNow": number }` (`reason` = the run-mode refusal text or the TZ notice; no secrets, no zone name). `insert ... on conflict (key) do update set value = excluded.value, updated_at = now()`. Make sure nothing in the web Settings code breaks on an unknown key.
4. **Posting-status banner (web).** `apps/web/lib/status/posting.ts`: `loadPostingStatus(pool, now)` → `{ state: "live" | "dry-run" | "stale" | "unknown", lastTickAt, missed }` where `stale` = `lastTickAt` older than 5 min, `unknown` = no row. Missed count = approved items, `scheduled_for < now − 60 min`, platform ≠ snapchat, batch approved (compute in SQL, don't trust the heartbeat number). Banner on Home (top, above the captions strip) and Calendar (above the grid):
   - `dry-run`: warn, "Posting is off (dry run). Approved posts won't go out." + "Turn it on: set DRY_RUN=false and WORKER_LIVE=1 on the server, then restart the worker."
   - `stale`/`unknown`: danger, "The worker hasn't checked in since <local time> — nothing is posting." / "The worker hasn't reported yet."
   - `missed > 0`: warn, "N approved posts missed their time" → link to the calendar on the oldest missed post's week.
   - `live` and fresh, nothing missed: no banner on Home; on Calendar a small muted "Posting is on" line.
   Calendar cards: an approved item past `scheduled_for − 0` by > 60 min and not published shows a "Missed" chip (warn tone); the existing Move action reschedules it (check that moving an approved item keeps it approved and re-arms it; if it doesn't, say so in your report — don't change the transition rules).
