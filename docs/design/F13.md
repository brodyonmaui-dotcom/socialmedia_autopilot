# F13: Go-live readiness (preflight, tick lock, YouTube existence check, first-real-post runbook)

Status: draft (Fable run 3 wrap-up, 2026-11-14). Fable leads and gates it; Opus implementers build. Line numbers are for branch `fable/run-3-2026-11-14`; re-grep before citing. **No migration.**

## Where we start
- **Why now.** M1's "IG + YT posting for real by Nov 21" (`docs/m0-plan.md`) is the milestone at risk. What blocks it is creator tasks scattered across `docs/runbooks/` (migrations, login, alerts-push, token-renewal, restore, deploy). The exit criteria still open: "backup and restore proven" and a phone demo checklist.
- **Outbox.** `runOutboxWith` (`apps/worker/src/jobs/outbox.ts:288`) skips the tick when `isValidMediaBase` (`:243`) fails and raises one `config` alert (`raiseConfigAlert`, `:261`). Otherwise it loads cadence and calls `runOutboxTick`. There is no lock: `registerOutboxJob` (`register-outbox.ts:6-18`) calls `boss.work(QUEUES.outboxTick, ...)` with no options and schedules `* * * * *`. `claim()` is conditional (`outbox.ts:130`) so no row fires twice, but two overlapping ticks can each read the same daily count and exceed a cap by one (F7 A9).
- **Existence checks.** Only Instagram has `findExisting` (`packages/adapters/src/instagram.ts:133-142`: last 25 media, normalised caption, within +-36 h of `scheduledFor`). YouTube has none (`packages/adapters/src/youtube.ts:37`, test `youtube.test.ts`), so a timed-out upload stays `unknown` until the human checklist (F11).
- **YouTube uploads playlist: not verified.** `docs/research.md` documents no `channels.list` / `playlistItems.list` lookup. The only mention is the F9 T1 probe line `video_stats_shape` ("found via the uploads playlist; +2 quota units", `research.md:198`), whose output the creator hasn't pasted yet. See OQ3.
- **Facts the preflight can read.** Migrations: `schema_migrations(id, applied_at)` (`docs/runbooks/migrations.md`), files `0001`-`0008` in `packages/db/migrations/`. Passkeys: `auth_credentials` (`0006_auth_approval.sql:5`). Run mode: `DRY_RUN`, `WORKER_LIVE` (`.env.example:8,10`, `apps/worker/src/run-mode.ts`). VAPID names `.env.example:45-48`. Cadence: `normalizeCadence` (`packages/core/src/cadence.ts:86`). Backup: `infra/backup.sh` prints `backup ok <ts> <size>` and writes `s3://$R2_BUCKET_BACKUPS/db/autopilot-<ts>.sql.gz`; `infra/restore-test.sh` prints `restore ok <key> tables=<n>` and leaves no marker.
- **Probe log.** `docs/research.md` has dated headings (e.g. "### M0 result - Instagram (2026-11-10, probe on the VPS)", "### First real Instagram post ... (2026-11-12, live)"), not a machine-readable table (OQ4).

## Goals
1. **One preflight command** that turns the scattered creator tasks into PASS/WARN/FAIL lines, each FAIL with the exact next command or runbook. Read-only; prints no secret value.
2. **No cap overshoot from overlapping ticks.** A second concurrent outbox tick does nothing and says so.
3. **YouTube `findExisting`** so the YT branch of F11's "unknown" state is also checked by code, mirroring Instagram's shape. It only ever avoids a resend.
4. **A first-real-post runbook** so the first IG reel and first YT private upload follow one written gate (chat OK, checks, rollback).

## Non-goals
- Posting, connecting accounts, or switching the run mode. The preflight only reports `DRY_RUN` / `WORKER_LIVE` state (non-negotiables 2 and 6).
- A web page for the preflight (CLI + VPS wrapper only).
- Auto-fixing a FAIL. It prints the command; the creator runs it.
- A TikTok or Snapchat existence check (TikTok relies on the Zernio key; Snapchat never reaches the outbox).
- Verifying Meta token scopes (stays with `token-health`).

**Env names the preflight checks (names only):** `DATABASE_URL`, `PUBLIC_MEDIA_BASE` (also via `isValidMediaBase`), `TZ_CREATOR`, `DRY_RUN`, `WORKER_LIVE`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, plus the per-platform adapter names that `credentialsFromEnv` reads (import them; don't copy the list).

**Checks (id: rule).**
- `env`: every required name set and non-empty. FAIL lists names only.
- `media-base`: `isValidMediaBase`. FAIL points at `.env` and a worker restart.
- `tz`: `TZ_CREATOR` non-empty and accepted by `Intl.DateTimeFormat`. The value is never printed.
- `migrations`: every expected file is in `schema_migrations`. FAIL points at `docs/runbooks/migrations.md`.
- `passkey`: `auth_credentials` count >= 1, else `docs/runbooks/login.md`.
- `run-mode`: PASS prints the state in words ("dry-run: nothing publishes"). Being live is a WARN, never a FAIL; being dry is never a FAIL.
- `vapid`: all three set, else WARN (`docs/runbooks/alerts-push.md`).
- `backup`: newest backup < 24 h, else FAIL (`docs/runbooks/restore.md`); unknown = WARN.
- `restore-drill`: a recorded drill exists (OQ2), else FAIL.
- `cadence`: settings parse via `normalizeCadence`; caps and `slotsPerDay` in range.
- `probe-log`: per platform (ig, yt, tiktok) a dated entry < 30 days (OQ4), else WARN with the `./infra/probe.sh <ig|yt|tiktok>` command.

## Data model
No new table or column. One optional settings key `restore_drill_at` (ISO string) written by `infra/restore-test.sh` on success (OQ2). `schema_migrations`, `auth_credentials` and `settings` are read only.

## Acceptance criteria (whole item)
1. `./infra/preflight.sh` on the VPS prints one line per check and exits 1 on any FAIL; no env value or token appears (leak scan on a captured run).
2. Two overlapping outbox ticks never exceed a daily cap (DB test).
3. A timed-out YT upload is looked up by code before any resend; a hit records it, a miss leaves the row for the creator.
4. The first-real-post runbook exists and the creator can follow it from the phone.
5. `pnpm typecheck`, `pnpm test`, `pnpm simulate-week` are green. Default stays dry-run.

## Open questions (recommended default in **bold**)
Lead review 2026-11-14: every bold default is approved as written.

1. **How does the lock get connection affinity?** `OutboxPool.query` is a plain pool, so lock and unlock could land on different connections. **Check out one client with `pool.connect()` for the lock only (the tick keeps using the pool) and release in `finally`.** `OutboxPool` gets an optional `connect()`; fakes without it skip the lock and log once.
2. **Where does the restore-drill marker live?** None exists today. **`restore-test.sh` writes `settings.restore_drill_at` on success.** A file under `logs/` fails because the preflight may run in a container that can't see it.
3. **Is the uploads-playlist lookup documented?** Not in `research.md`. **Verify at build time (non-negotiable 7) against the official docs for `channels.list` (`part=contentDetails`, `relatedPlaylists.uploads`) and `playlistItems.list` (`part=snippet`, `maxResults=25`): quota (expected 1 unit each), whether private and scheduled videos appear in the owner's uploads playlist, and how soon after upload. Log the result in `research.md`. If private/scheduled items don't appear for the owner, drop T3 and say so.** Reuse the F9 probe's lookup if its shape was confirmed by the pasted `yt.video_stats_shape` line.
4. **How does the preflight read the probe log?** It is prose. **Match the newest `(YYYY-MM-DD` in a heading that names the platform; WARN (not FAIL) when stale or absent.** Later: a small `docs/probe-status.json` kept by the probe wrapper.
5. **WARN or FAIL for run-mode state?** **Neither for dry-run (PASS with the state in words); WARN when live**, so nobody misses it.
6. **Does the preflight need network (backup age)?** **Only through the wrapper's `docker compose exec backup aws s3 ls`**, as `restore-test.sh` does. The script stays offline and receives `lastBackupAt`.
