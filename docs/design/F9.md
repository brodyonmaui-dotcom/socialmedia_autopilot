## Goals
1. **Read-only probe lines** (run by the creator) that print the **shape** (key paths + JSON types, never values, ids or names) of one live response per source:
   - `./infra/probe.sh ig` adds `reel_insight_shape` (one accepted metric on the newest reel, e.g. `data[].name:string,data[].period:string,data[].values[].value:number,data[].total_value.value:number`) and `media_fields_shape` (`like_count:number?,comments_count:number`).
   - `./infra/probe.sh yt` adds `video_stats_shape` (newest upload: `items[].statistics.viewCount:string,…`).
   - TikTok: none (manual metrics on the free plan).
2. **Fixtures and parsers updated to the probed shapes.** Record each shape in the `docs/research.md` verification log, with a `// verified <date> probe <line>` comment in `sources.ts`.
3. **Worker job `analytics-ingest`**, run hourly (`23 * * * *`, off the hour):
   - Load published posts from the last 30 days, then run `ingestOnce` with the configured sources (IG when Meta creds exist; YT with a fresh access token per run; TikTok only when `ZERNIO_ANALYTICS=1`, see OQ2).
   - Write snapshots and log one line: `[analytics] captured n · failed n (ig n, yt n) · no-source n`.
   - At most 50 posts per run, oldest-due first, so a backlog can't burst the IG rate limits.
4. **Per-platform failure reporting.** `ingestOnce` returns `failedByPlatform` and a sanitised `lastErrorByPlatform` (≤ 200 chars) instead of swallowing errors.
5. **A `metrics-health` alert** when a platform's source fails in **3 consecutive runs**:
   - A run "fails" for a platform when every attempted fetch failed. A run with at least one success resets the counter.
   - The counter lives in the settings KV `metrics_health = {platform: {consecutive, lastOkAt}}`.
   - The alert has one open row per platform, uses the engagement-style dedupe on kind + platform while it's open, and its message is sanitised.
   - It's added to `AlertKind`. It is page-only unless F8's push kinds are changed.

## Non-goals
- TikTok metrics on the free plan (the creator checks the app). Snapchat metrics.
- YouTube Analytics API watch time (a new source plus a quota review; later).
- Back-filling missed checkpoints (`dueAge` rule stays).
- New tables, or changes to `/analytics` beyond what real data naturally shows.

**Rules**
- Read-only: only GETs, plus the YT token refresh POST (no side effects). The job therefore runs regardless of `DRY_RUN` and the worker live key (OQ1). Its startup line says `analytics=read-only`.
- No tokens in logs or alerts: errors go through the sanitiser, and URLs (IG puts the token in a header via `sources.ts`; check it isn't in the query) are never logged.
- An IG metric rejected for one reel (e.g. on old media) counts as a partial result, not a failure. `normalizeMetrics` (`store.ts:11`) fills the missing field with null.

## Data model
None new.
- `post_metrics` (0004) keeps `unique(batch_item_id, age_hours)`.
- `settings.metrics_health` is a KV row written via `setSetting` (`packages/db/src/settings.ts:11`).
- `alerts` gets kind `metrics-health` (free text) with `platform` = the platform.

## Open questions (recommended default in **bold**)
1. **Run ingest in dry-run too?** **Yes.** It's read-only (GETs) and touches no public state. The job says so in its startup line.
2. **TikTok via Zernio analytics?** **Off (`ZERNIO_ANALYTICS` unset).** It's free-plan manual. Turning it on needs one read-only call to check that it doesn't return 402, which is the creator's call (`docs/tiktok-free-plan.md:35`).
3. **Use `scheduled_for` as `postedAt` for IG?** **Yes for now.** IG fires at `scheduled_for` (± a minute). Revisit if retries push publishes hours late: store a `published_at` from the engine (needs a migration).
4. **Hourly vs every 6 h?** **Hourly.** The checkpoints are hour-granular, and IG costs about 9 requests per due post, which is tiny at about 30 posts a week.
5. **Push `metrics-health`?** **No (page-only).** Stale metrics aren't urgent.
